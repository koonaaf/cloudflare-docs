When you add an `NS` record to your zone, you create a **subdomain delegation**: you hand authority for that subdomain (and everything below it) to another set of nameservers. Any other records stored in your zone at or below that delegation point are **shadowed**: they stay in your zone, but Cloudflare never answers with them. Once authority is delegated, queries for that subdomain are referred to the external nameservers.

When an `NS` record hides other records at or below it, we say the `NS` record is **shadowing** and the hidden records are **shadowed**. These are two perspectives on the same delegation, not separate situations.

Shadowing is easy to introduce without realizing it. You might create a record under a subdomain expecting it to resolve, not knowing an `NS` delegation already shadows it. Or you might add an `NS` delegation without realizing it shadows records you already rely on. Cloudflare does not block you from creating or modifying records regardless of shadow relationships. Because Cloudflare cannot tell an intentional shadow from a mistake, it warns rather than blocks.

Shadow metadata tells you which records are shadowed, which `NS` records do the shadowing, and how many records a delegation hides. It is exposed as fields on API responses and as warnings in the Cloudflare dashboard. It is not returned unless you explicitly request it.

## Why shadowed records matter

Shadowed records are invisible to DNS resolvers. Consider this example:

```txt
sub.example.com    NS    ns1.example.org.
www.sub.example.com  A   192.0.2.1
```

The `NS` delegation at `sub.example.com` hands authority for everything at or below it to the external nameservers. Resolvers follow that delegation and never return your `A` record. The record exists in your zone but has no effect.

The problem cuts both ways. Adding an `NS` delegation can shadow records you already depend on. Adding records under an existing delegation produces records that never resolve. In both cases nothing errors out, which is what makes shadow metadata useful for spotting the issue.

Common situations that produce shadowed records:

- You added a delegation to point a subdomain at an external provider, but forgot to remove the existing records there.
- You removed a delegation but the external provider's records remained in your zone.
- You created records under a delegated subdomain thinking they would resolve from the parent zone.

## Glue records

A glue record is an `A` or `AAAA` record that is required to make a delegation work. Glue is needed when the nameserver hostname for a delegation falls within the delegated zone itself. Without it, a resolver asking "where is `ns1.sub.example.com`?" would follow the delegation for `sub.example.com` — which it cannot reach until it already knows `ns1.sub.example.com`. This is a circular dependency.

Consider this example:

```txt
sub.example.com    NS    ns1.sub.example.com.
ns1.sub.example.com  A   192.0.2.1
```

The `A` record for `ns1.sub.example.com` is glue. It is shadowed (the `sub.example.com` delegation takes effect first), but it serves a valid purpose: the parent zone publishes it alongside the delegation so resolvers can bootstrap the subdomain lookup.

Glue is only meaningful for `A` and `AAAA` records. A `CNAME` record at the same name as an `NS` target is not treated as glue.

## Dead glue

Dead glue is a glue record that exists in your zone but is never served, not even in the glue section. This happens when a shallower delegation (one closer to the zone apex, with fewer labels in its name) intercepts authority before the zone can answer for the name the glue is intended for.

Consider this example:

```txt
sub.example.com      NS    ns1.sub.example.com.
a.sub.example.com    NS    ns1.a.sub.example.com.
ns1.a.sub.example.com  A   192.0.2.1
```

The `A` record for `ns1.a.sub.example.com` looks like glue for the `a.sub` delegation. However, the shallower `sub.example.com` delegation intercepts all queries for anything under `sub.example.com`, including `a.sub.example.com`. The parent zone never gets to serve the glue for `ns1.a.sub.example.com`, so it is dead.

Dead glue does not cause resolution failures. It is either a leftover you can safely remove, or a signal that the shallower delegation was created in error.

:::caution
Before removing a record flagged as dead glue, verify that the external nameserver for the shallower delegation (`sub.example.com` in the example above) already holds the correct records for the deeper subdomain.
:::
